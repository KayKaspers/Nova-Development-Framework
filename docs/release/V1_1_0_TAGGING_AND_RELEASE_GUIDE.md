# v1.1.0 Tagging and Release Guide

## REFERENCE ONLY — NOT AUTHORISED FOR EXECUTION

This guide documents the manual steps a Human Maintainer would eventually take to tag and publish `v1.1.0`. **No AI agent, including the one that prepared this document, is authorised to execute any command in this guide.** This is documentation only, prepared during release prep (NDF-WP-159); it is not itself a release-execution contract. The actual executable Human-Maintainer command sequence for the eventual release will be generated by Nova after WP-159 review and Human-Maintainer acceptance — treat this guide as background reference for that later sequence, not as the active instruction to run now.

`v1.1.0` is **not** released, tagged, or published as of this document. `v1.0.0` remains the only final released version.

## Purpose

Manual guide for the **Human Maintainer** to tag and publish `v1.1.0`, if and when they decide to release it. The implementation agent that prepared this guide does not execute any of these steps — tagging, pushing the tag, and creating the GitHub release are exclusively human actions (ADR-0031/ADR-0032).

## Required Preconditions

- [`V1_1_0_GO_NO_GO.md`](V1_1_0_GO_NO_GO.md) reviewed by the Human Maintainer, with an explicit decision recorded (not `PENDING_HUMAN_DECISION`).
- Nova review of this WP-159 release-prep package completed, and its result (`GO` / `GO_WITH_NOTES` / `REWORK` / `BLOCKED`) accepted by the Human Maintainer.
- `main` verified clean on the actual intended release commit (not necessarily the WP-159 baseline commit above).
- `origin/main` verified equal to local `main` on that same commit.
- Public Quality Gate re-run and green (`--strict` and `--self-test`) on the actual release commit.
- `docs/release/V1_1_0_RELEASE_NOTES.md` re-reviewed on the actual release commit for accuracy (no stale commit hashes, no claim that has since become false).
- `CHANGELOG.md` carries an entry describing the released state (a dated `## [1.1.0]` section may need to be added at release time per NDF's existing convention of staging such sections only once a version is actually tagged — see the `v1.0.0`/`v0.9.0-foundation` precedent).
- `v1.1.0` tag does not already exist.
- GitHub secret `NDF_PUBLIC_NEUTRALITY_DENYLIST` is configured (CI-side neutrality check).

## Verify Clean Main

```bash
git status
git checkout main
git pull origin main
```

Expected: clean working tree, no pending changes, `main` up to date with `origin/main`.

## Verify Local/Remote Equality

```bash
git rev-parse HEAD
git rev-parse origin/main
```

Expected: both commands return the same commit hash — the actual intended release commit.

## Final Public Quality Gate

```bash
python scripts/check_public_quality.py --strict
python scripts/check_public_quality.py --self-test
```

Expected: both pass with 0 errors (warnings/notices reviewed, not necessarily zero — compare against the WP-159 baseline run of 0 errors / 0 warnings / 3 notices and investigate any new warning or error).

## Final Release Artifact Review

- Re-read `docs/release/V1_1_0_RELEASE_NOTES.md` in full on the actual release commit; confirm no claim has become stale (commit hashes, "not released" language, known limitations still accurate).
- Re-read `docs/release/V1_1_0_GO_NO_GO.md`; confirm the Human-Maintainer decision section is filled in with an actual decision and date.
- Re-read `docs/release/V1_1_0_RELEASE_EVIDENCE_INDEX.md`; confirm every cited source file still exists at its stated path.
- Confirm `CHANGELOG.md` reflects the release accurately.


```bash

```

## GitHub Release Publication Step

Manual, in the GitHub UI (**Releases → Draft a new release**, tag `v1.1.0`, target `main`), or as a Human-Maintainer-decided CLI step (human-maintainer-only option, not to be executed by any agent):

```bash
gh release create v1.1.0 --title "Nova Development Framework v1.1.0" --notes-file docs/release/V1_1_0_RELEASE_NOTES.md
```

The Human Maintainer decides "pre-release" vs. "final" and "set as latest release" at this step, based on their own judgment of v1.1.0's maturity — this guide does not presume either choice.

## Post-Release Verification

- [ ] Release appears on GitHub with tag `v1.1.0` on `main`, with the release type (pre-release/final, latest/not-latest) matching the Human Maintainer's actual decision.
- [ ] Release title is "Nova Development Framework v1.1.0".
- [ ] Tag is annotated (`git cat-file -t v1.1.0` → `tag`).
- [ ] Release body matches `V1_1_0_RELEASE_NOTES.md`'s content on the actual release commit.
- [ ] Public Quality Gate CI check on the release commit is green.
- [ ] `git tag` lists `v1.1.0` alongside all prior tags (`v0.1.0-foundation` … `v1.0.0`), none moved or altered.

## Rollback / STOP Conditions

**STOP before tagging if any of the following is true:**

- The Go/No-Go decision is not an explicit `GO` or `GO_WITH_NOTES` from the Human Maintainer.
- `main` is not clean, or `origin/main` does not match local `main`.
- The Public Quality Gate fails (`--strict` or `--self-test`).
- Any release-prep artifact contains a claim that release semantics scanning would flag as premature (e.g., "v1.1.0 released" appearing before this guide's steps are executed).
- A material change has occurred since WP-159's baseline that this guide's artifacts do not reflect (in which case the release-prep package should be refreshed before tagging, not patched ad hoc at tag time).

**If tagging or release proceeds and something is found wrong afterward:**

- **Release text/title wrong:** edit the GitHub release directly (no Git action needed).
- **Wrong tag state, not yet publicly used:** delete the release, then delete and re-create the tag:

```bash
git tag -d v1.1.0
git push origin :refs/tags/v1.1.0
```

- **Already publicly used:** do **not** move the tag; **no history rewrite**. The Human Maintainer decides on a correction release (e.g., `v1.1.1`) or a documented reconciliation, following the same pattern used for prior NDF releases.

## Post-Release Follow-up

After tag + release, NDF's established pattern is a dedicated post-release review work package (analogous to WP-149 for `v1.0.0` and WP-133 for `v0.9.0-foundation`): read-only verification of the published tag and release, confirmation of any known-limitation status, and lifting current-state documents to reflect the actual released state. That work package does not yet exist and is not created by this guide — it would be planned separately, after an actual release.
